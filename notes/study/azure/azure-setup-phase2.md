## 2-1：Azureに関する方針・命名規則を定める
 
### リージョン
 
| 項目 | 値 |
|------|-----|
| 使用するリージョン | `japaneast`（東日本） |
| 選定理由 | 国内ユーザー向けに最も近いリージョン |
 
### 命名規則
 
Azureリソースには名前をつける必要があり、命名の制約は公式ドキュメントで確認できる。  
[Azure リソースの名前付け規則と制限事項 - Microsoft Learn](https://learn.microsoft.com/ja-jp/azure/azure-resource-manager/management/resource-name-rules)
 
 
Blob Storageアカウントは他のリソースとフォーマットが異なる。  
(Azure全体で一意かつハイフン不可・小文字英数字のみという制約がある)

### 各リソースの命名一覧
 
| リソース | 名前 | 一意の範囲 |
|---------|------|-----------|
| リソースグループ | `myazure-rg` | サブスクリプション内 |
| Static Web Apps | `myazure-swa` | サブスクリプション内 |
| Blob Storageアカウント | `myazurestorage` (**注**) | Azure全体 |
| Blobコンテナ | `entries` | ストレージアカウント内 |

(**注**) 他のユーザーによって使用されている場合は別の名前に適宜変更する。(myazurestorage12345など)

## 2-2：Azureアカウントを作成する
 
Microsoftアカウントを作成してから、そのMicrosoftアカウントでAzureアカウントを作成すると良い。Azureでは無料アカウントも提供されているが、クレジットカードの登録は必要となる。無料アカウントから始めて、30日後に従量課金制へアップグレードする、といったことも可能。

### Azureアカウント作成時の注意点
 
| 項目 | 内容 |
|------|------|
| 無料の内容 | 作成後30日間有効な200ドル分のクレジット＋一部サービスが12ヶ月無料 |
| カードの用途 | 本人確認のため。無料枠を超えない限り自動課金されない |
| 使用アカウント | 既存のMicrosoftアカウント（GitHubアカウントも可能だが使用しなかった） |
 


### Azureアカウント作成手順
 
1. ブラウザで `https://azure.microsoft.com/ja-jp/` にアクセスする
2. 「Azureの使用を開始する」→「Azure 無料アカウント」→「Azureを無料で試す」へ進む
3. 既存のMicrosoftアカウントでサインインする
4. 氏名・電話番号・住所などの情報を入力する
5. クレジットカード情報を入力する（無料期間中は課金されない。本人確認のため必要）
6. 規約に同意してアカウントを作成する
 

 
### Azure管理の階層構造について
 
Azureポータルには「リソース管理」と「課金管理」という2つの切り口が混在しており、初見で混乱しやすい。  
それぞれの階層構造を以下に整理する。
 
**リソース管理の切り口** 
- Azureアカウント作成時にサブスクリプションまでは自動的に構成済み
- 本フェーズではリソースグループ以下を作成していく
```
Microsoftアカウント (yamada)                    #Azureのログインに使う、例:yamadaさん
 └── Azure Tenant (Entra ID)                  #Azure上の組織。ユーザーやアクセス権を管理する
     └── Entra IDユーザ (yamada)               #テナント内のユーザー。リソース操作の主体
         └── サブスクリプション subscription1    #リソースをまとめる単位。課金もここ単位。
             └── リソースグループ:myazure-rg     #リソースをまとめる「フォルダ」
                 ├── Static Web Apps          #実際に使うサービス1 
                 └── Blob Storage             #実際に使うサービス2
```
 
**課金管理の切り口** 
- Azureアカウント作成時に自動的に全て構成済み 
```
Microsoftアカウント (yamada)                    #Azureのログインに使う
 └── 課金アカウント (yamada)                     #課金管理の起点。Azure登録時に自動作成
      └── 課金プロファイル                       #請求先住所・クレジットカード情報などを保持
           └── 請求書セクション                  #請求書の分類単位
                 └── subscription1            #リソース管理の文脈と合流
```
 
**2つの切り口のつながり**
 
- サブスクリプションは両方の切り口に登場する共通のキー
- リソース管理側では「リソースをどこに置くか」の単位
- 課金管理側では「誰にいくら請求するか」の単位
- サブスクリプションが、リソース側と課金側をつなぐ

## 2-3：リソースグループを作成する

### はじめに
ここからAzureで具体的なリソースの作成を行なっていく。リソース管理は方法が２通りある。

- ブラウザでAzureポータルを開いて管理する
- Azure CLIというコマンドラインツールを導入してコマンド発行で管理する

本文書では、**Azureポータルで管理を行う**こととする。

### リソースグループとは
 
Azureのリソース（Blob Storage・Static Web Appsなど）をまとめて管理するための「フォルダ」のようなもの。リソースグループを削除すると、その中のリソースもまとめて削除される。
 
### リソースグループの作成手順
 
1. 検索窓に「リソースグループ」と入力して選択する
2. 「＋作成」をクリックする
3. 以下の項目を入力する
 
| 項目 | 値 |
|------|-----|
| サブスクリプション | 使用するサブスクリプションを選択 |
| リソースグループ名 | `myazure-rg` |
| リージョン | `Japan East` |
 
4. 「確認および作成」→「作成」をクリックする
5. 一覧に `myazure-rg` が表示されれば成功

## 2-4：Static Web Appsリソースを作成する
 
### Static Web Apps(SWA)とは
 
フロントエンド（HTML・CSS・画像）の配信と、Azure Functionsによるバックエンド処理を一体として提供するサービス。
 
### GitHubなどとの連携とデプロイ
 
GitHubと連携することで、コードの変更を契機にGitHub側からAzureへの自動ビルド・デプロイを行う運用が可能であり、CI/CDとの親和性が高いことが特徴の一つである。
 
方法は3つある
- GitHub  
  - AzureがGitHubとOAuthで連携する
  - SWA作成時、GitHubにワークフローやデプロイトークンが自動で配置される
  - Azureに対し**GitHub全体のアクセスを許可**する必要がある
- Azure DevOps  
  - Azure のソフトウェア開発基盤であるAzure DevOpsを利用する
- その他  
  - SWAのデプロイトークンを自分でGitHubなどに配置、ワークフローを自ら作成する
  - ただし、「その他」を選んだ場合、スクリプトが動作しない模様

> ⚠️注意：  
> 3つ目の「その他」を選んだ場合は、本来SWAと連携するはずのAzure Functionsが動作しないようである。  
> その結果、SWAだけが動くため、HTML/CSSはデプロイされるも、スクリプトがデプロイできない。  
> Azure Functions単体でもリソース作成可能だが、従量課金制へアップグレードが必要。

あえてGitHub連携やAzure DevOpsを利用せず、自身でデプロイトークンをGitHubに配置しワークフローも別途用意する方針も検討したが、**最終的にGitHub連携を行うこととした**。
 
 
### SWAの作成手順
 
1. 検索窓に「Static Web Apps」と入力して「静的 Web アプリ」を選択する
2. 「＋作成」をクリックする
3. 以下の項目を入力する
 
| 項目 | 値 |
|------|-----|
| サブスクリプション | 使用するサブスクリプションを選択 |
| リソースグループ | `myazure-rg` |
| 名前 | `myazure-swa` |
| ホスティングプラン | `Free`（デフォルトが`Standard`になっているので変更する） |
| デプロイの詳細（ソース） | `GitHub` |

4. 「GitHubアカウントでサインイン」をクリックし、GitHub側で「Authorize AzureAppService」をクリックして認証する。このとき、特定のリポジトリではなく**GitHubアカウント全体へのアクセスを許可する**ことになる点に留意すること。
5. 以下の項目を入力する

| 項目 | 値 |
|------|-----|
| 組織 | GitHubのユーザー名または組織名 |
| リポジトリ | `myazure` |
| 分岐 | `main` |
| ビルドのプリセット | `Custom`（今回はフレームワークを使わないため） |
| アプリの場所 | `/frontend` |
| APIの場所 | `/api` |
| 出力先 | 空欄のまま |


6. 「次：デプロイ構成」タブで「デプロイ認可ポリシー」を`デプロイトークン`とする。
7. 「次：詳細設定」タブで「Azure Functions APIとステージング環境のリージョン」が`East Asia`になっていることを確認する。無料アカウントのためエンタープライズレベルのエッジはオフのまま。
8. 「確認および作成」→「作成」をクリックする。
9. デプロイ完了後、リソースページのURLに `*.azurestaticapps.net` 形式のURLが表示されれば成功。
10. GitHubリポジトリに下記の内容が自動生成されていることを確認する。SecretsはリポジトリのSetting - Secrets and variables - Actionで確認できる。

| 確認項目 | 状況 |
|---|---|
| yml追加 | .github/workflows/azure-static-web-apps-<固有URL>.yml |
| Secrets追加 | AZURE_STATIC_WEB_APPS_API_TOKEN_<固有名> |
| Actions | .ymlがpushされたことでワークフローが動くがエラーとなっている |


### 補足：GitHubとのOAuth連携時の機能拡張
AzureでGitHubにOAuth認証する方式の場合、GitHubのワークフローにおいて、ブランチに対する補佐機能が提供される。
main(Product)に対しブランチを作成しPRを行うと、Azure SWA側で一時的なURLが用意され、ブランチの内容をそこにデプロイすることで確認作業ができるという機能であり、Product/Stagingのブランチ利用に有用である。

## 2-5：Blob Storageアカウントを作成する
 
> ⚠️注意： Blob Storageはフェーズ３以降で使用する

### Blob Storageアカウントとは
 
Blob Storageを使うために必要な「入れ物」。この中にコンテナ（フォルダ）を作り、その中にデータ（Blob）を保存する。
 
### Blob Storageアカウントの作成手順
 
1. 検索窓に「ストレージアカウント」と入力して選択する
2. 「＋作成」をクリックする
3. 以下の項目を入力する
 
| 項目 | 値 |
|------|-----|
| サブスクリプション | 使用するサブスクリプションを選択 |
| リソースグループ | `myazure-rg` |
| ストレージアカウント名 | `myazurestorage`（作成時に変更する可能性あり） |
| リージョン | `Japan East` |
| 優先ストレージの種類 | `Azure Blob Storage または Azure Data Lake Storage Gen 2` |
| プライマリワークロード | `クラウド ネイティブ` |
| パフォーマンス | `Standard`（汎用v2アカウント） |
| 冗長性 | `ローカル冗長ストレージ（LRS）` |
 
4. 「次へ」で詳細タブに進み、「個々のコンテナーでの匿名アクセスの有効化を許可する」がオフになっていることを確認する
5. 「次へ」でネットワーク・データ保護・暗号化・タグタブは全てデフォルトのまま進む
6. 「レビューと作成」をクリックする
7. 名前が重複している場合はこの時点でエラーとなる。その場合は「前へ」で戻ってストレージアカウント名を変更して再試行する
 
**名前が既に使われていた場合**
 
「レビューと作成」をクリックした際に以下のようなエラーが表示された場合は、名前が他のユーザーに使用されている。
 
```json
{
  "code": "StorageAccountAlreadyTaken",
  "message": "The storage account named myazurestorage is already taken."
}
```
 
「前へ」で基本情報タブに戻り、ストレージアカウント名を変更して再試行する（例：`myazurestorage2`、`myazurest20260325` など重複しにくい名前）。
 
8. 「作成」をクリックする
9. デプロイ完了のメッセージが表示されれば成功

## 2-6：Blobコンテナを作成する

> ⚠️注意： Blobコンテナはフェーズ３以降で使用する
 
### Blobコンテナとは
 
ストレージアカウント内の「フォルダ」にあたるもの。今回はユーザーが登録したテキストデータを1件ずつBlob（ファイル）として保存する場所として使用する。
 
### Blobコンテナの作成手順
 
1. 作成したストレージアカウント（`myazurestorage`）を開く
2. 左メニューの「データストレージ」セクションから「コンテナー」を選択する
3. 「＋コンテナーの追加」をクリックする
4. 以下の項目を入力する
 
| 項目 | 値 |
|------|-----|
| 名前 | `entries` |
| 匿名アクセス レベル | プライベート（匿名アクセスはありません）（デフォルトのまま） |
 
ストレージアカウント作成時に匿名アクセスを無効にしているため、匿名アクセス レベルのドロップダウンはグレーアウトしており変更できない。詳細設定はデフォルトのままにする。
 
5. 「作成」をクリックする
6. 一覧に `entries` が表示されれば成功
