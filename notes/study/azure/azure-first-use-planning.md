## CI/CDの方針
本構成ではCI/CDとしてGitHub Actionsを採用する。  
詳細なワークフロー設計は構築フェーズで検討するが、現時点での方針は以下の通り。  
以降のステップで後述するが、今回はAzureに対しGitHub全体を連携させる手法を行っている。  
(Azure無料アカウントの場合、この手法に限定されるように思われるが詳細は不明)

| 領域 | 担当 |
|------|------|
| ビルド・デプロイ（CI/CD） | GitHub Actions |
| 実行環境 | Azure |
| ブランチ 本番(main)  | Azureで実行する |
| ブランチ 開発(dev) | Azureで実行する |


**注意**  
本格的な開発に際してはローカルでの実行環境を別途用意すべきところ、今回は開発(dev)もAzure上に配置し実行するという特殊な構成としている。(初めてAzureを使ってみる、という目的を優先)

## Azureサービス構成

### Azureの採用サービスと役割分担

| 役割 | 採用サービス | 採用理由 |
|------|-------------|---------|
| 静的ファイル置き場＋フロントエンド配信 | Azure Static Web Apps | カスタムドメイン・SSL・GitHub ActionsのCI/CD自動化との相性が良い |
| バックエンド処理（登録・表示） | Azure Functions | Static Web Appsと同一ドメインで統合できる・TypeScript正式対応・サーバーレスでコスト低 |
| データ保存 | Azure Blob Storage | シンプルな構成・TypeScript SDKが整備されている |

```
[ユーザーのブラウザ]
      ↓ HTML/CSSを取得
[① Azure Static Web Apps]
      ↓ 登録・表示のAPIリクエスト（同一サービス内で完結）
[② Azure Functions（TypeScript）]
      ↓ テキストデータの読み書き
[③ Azure Blob Storage]
```
 
### Static Web AppsとAzure Functionsの関係  
- Azure Functionsは独立したサービス
- Static Web Appsと統合可能
  - 同一ドメイン配下（`/api/*`）で呼び出すことが可能
  - フロントエンドとAPIが同一サービス内に存在するように見える
  - 実体としては別サービスが連携して動作している。

## データの流れ

以下のような登録・表示の流れを行う。
実装の詳細は以降のフェーズで決定するものとする。

### 登録の流れ
 
```
① ユーザーがテキストボックスに文字を入力して「登録」ボタンを押す
      ↓
② ブラウザからAzure FunctionsのAPIにリクエストが送られる
      ↓
③ Azure Functionsがテキストと登録日時をセットにしてBlob Storageに保存する
```
 
### 表示の流れ
 
```
① ブラウザがページを開く（または登録後に画面を更新する）
      ↓
② ブラウザからAzure FunctionsのAPIにリクエストが送られる
      ↓
③ Azure FunctionsがBlob Storageからデータを読み込む
      ↓
④ 登録の新しい順に5件を抽出してブラウザに返す
      ↓
⑤ ブラウザが5件のテキストと登録日時を表示する
```

## データ保存設計

### 保存先
本アプリケーションでは、Azure Blob Storageをデータ保存先として使用する。

- 1件の投稿 = 1つのBlobとして保存する
- Blobの保存や取り出しについてはこの段階では詳細化しない

### 補足：将来的な拡張について

Blob Storageはデータベースのようなクエリ機能を持たない。  
本構成はシンプルな構成を優先してBlob Storageを採用しているが、複雑な検索（全文検索・条件検索）、ページネーション、データ件数の大幅増加といった要件が発生した場合は別サービスの検討が必要となる。  
その場合は、Azure Table Storage や Azure Cosmos DB などのデータベースサービスへの移行を検討する。
