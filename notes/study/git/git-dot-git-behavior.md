## `.git`ディレクトリ？

`git init`や`git clone`を実行すると、そのフォルダの直下に`.git`という隠しディレクトリが自動的に作られます。Gitはこのディレクトリをリポジトリの設定フォルダとして使い、コミット履歴や設定情報などをすべてここに保存します。

`.git`ディレクトリの中にはGitが期待する特定の構造が必要です。主なものは以下の通りです。

| ファイル・フォルダ | 役割 |
|---|---|
| `HEAD` | 現在チェックアウトしているブランチへの参照 |
| `objects/` | コミットやファイルの実体データ |
| `refs/` | ブランチやタグの参照情報 |
| `config` | そのリポジトリ固有のGit設定 |

Gitはこの`.git`ディレクトリを見つけると、そこから上記の構造を読み込んでリポジトリとして認識します。逆に`.git`ディレクトリが存在していても、この構造が揃っていなければGitはそこを正しいリポジトリとして認識しません。

### Gitは`.git`ディレクトリを上に向かって探す

Gitコマンドを実行すると、Gitはまずカレントディレクトリに`.git`ディレクトリがあるかを確認します。なければ親ディレクトリ、さらにその親ディレクトリと、ルートディレクトリに到達するまで上に向かって`.git`ディレクトリを探し続けます。これはGitが「自分が今どのリポジトリの中にいるか」を特定するための動作です。

この動作があるからこそ、リポジトリ内のどの深さのディレクトリにいてもGitコマンドが使えます。たとえば以下のような構造の場合、

```
/Users/ユーザー名/Projects/tech-note/   ← ここに.gitがある
    └── docs/
          └── memo/   ← ここでgitコマンドを実行
```

`memo/`ディレクトリでGitコマンドを実行しても、Gitは親ディレクトリを遡って`tech-note/`の`.git`を見つけ、正しくGitコマンドが機能します。

どのgitコマンドを実行しても`.git`を探す動作は発生します。`git rev-parse --git-dir`でその結果を確認できます。

```bash
git rev-parse --git-dir
```

`.git`ディレクトリが存在しない場所で実行すると以下のようなエラーが返ってきます。

```
fatal: not a git repository (or any of the parent directories): .git
```

エラーメッセージの中の`or any of the parent directories`という文言が、Gitがカレントディレクトリだけでなく親ディレクトリまで遡って`.git`を探したが見つからなかった、ということを示しています。

## 気になったこと：`.git`という名前はGit限定ではない

世界中で広く使われているGitですが、調べていてひとつ気になる点がありました。

`.git`という名前はGitプロジェクトが使っている名前ですが、当然ながらOSやファイルシステムのレベルで「この名前はGit専用」として予約・保護されているわけではないことでしょう。

つまり理屈の上では、Git以外のソフトウェアが`.git`という名前のディレクトリを作ることを禁じるルールはどこにも存在しません。そのようなソフトウェアが実際に存在した場合、システムのあちこちにGitが想定する構成の`.git`とGitと無関係の`.git`が混在する状況も起こり得ます。

仮にGitと無関係な`.git`ディレクトリが存在する場所でgitコマンドを実行した場合、Gitがその`.git`を自身の設定フォルダと認識しようとして予期しない動作をする可能性があります。

OSレベルで名前を予約するか、Gitの設定ファイルで管理対象を明示的に指定する方式もあり得るとは思いますが、Gitが作られた当時はそういった設計が一般的ではなかったのかもしれません。このあたりは自分にはまだよくわかっていません。

## 対処手段として`$GIT_DIR`という環境変数の存在を知った

調べていたら`$GIT_DIR`というGitの環境変数を見つけました。これを設定すると、Gitに対して「設定フォルダはここにある」と明示的に伝えることができ、Gitがカレントディレクトリから親ディレクトリへ向かって`.git`を探す動作を抑制できます。

設計思想として理解しておく価値はあると感じたのですが、実用上は以下の2つの理由から断念しました。

ひとつは複数リポジトリを扱う環境との相性の問題です。`$GIT_DIR`はシェルの環境変数として設定するものなので、複数の独立したリポジトリを扱う環境では、リポジトリを切り替えるたびに`$GIT_DIR`を手動で書き換える必要があり、現実的な運用として成立しません。`git worktree`という機能も調べてみましたが、これはひとつのリポジトリ内で複数のブランチを別々のディレクトリで扱うための機能であり、複数の独立したリポジトリを`$GIT_DIR`で管理する問題の解決手段にはなりませんでした。

もうひとつはVS Codeとの相性の問題です。環境変数`$GIT_DIR`でGitが動作するようにした場合、VS Codeの挙動にどういった影響があるかよくわかっていません。VS Codeがリポジトリを自動検出できなくなるなどしたら、そもそもVS Codeを使うメリットそのものが損なわれますので。

## 結論

上記の検討を経て、Gitのデフォルトの動作、つまり`git init`や`git clone`の際に`.git`ディレクトリが自動的に作られ、Gitがそれを見つけて管理対象とする方式で進めることにしました。

とはいえ、`.git`という名前がGit限定でないという認識は心の奥に留めておこうかなと。

このことによって想定外の挙動や不利益が発生した場合でも、初学者の自分がGitの挙動を十分に把握していなかったのであれば、やむを得ないかなとは思います。いろんなパッケージを導入する際に、そこまでいちいち事前確認するわけでもないですし。

ただ少なくともどのディレクトリでどのコマンドを実行するかはユーザー自身が把握しておくべきことなので、実行前に現在地を確認する習慣をつけておくことを最低限の対処としておこう。
