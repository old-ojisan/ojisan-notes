## 1. 前提整理

Docker は OS 上で動作するアプリケーションであるが、
単なるユーザーアプリではなく、以下の特徴を持つ。

- Linux カーネル機能（cgroups / namespaces 等）に深く依存
- ネットワーク・ストレージ・プロセス管理に影響
- 実行基盤として他のアプリケーションを内包

そのため、**導入方法の選択は運用・セキュリティ・再現性に直結する**。

---

## 2. Dockerの主なインストール方式

Docker のインストール方式は、概念的に以下の 3 つに分類できる。

### 2.1 Docker 公式インストールスクリプト

- 公式が提供するスクリプト`get-docker.sh`を実行する方式
- OS 判別からリポジトリ設定、インストールまで自動化

**特徴**
- 非常に簡単
- 内部処理が見えにくい
- 学習・検証用途向け

---

### 2.2 OS 標準リポジトリ

- OS（Debian / Raspberry Pi OS 等）が管理するパッケージを利用
- `docker.io` などとして提供される

**特徴**
- OS 全体との整合性が高い
- バージョンが古くなりやすい
- Docker 公式ドキュメントとの差分が出やすい

---

### 2.3 Docker 公式リポジトリ（手動設定）

- Docker が管理する公式 APT リポジトリを明示的に追加
- apt を用いてインストール

**特徴**
- 手順が明確
- 公式想定構成で導入できる
- 再現性・説明性が高い

---

## 3. なぜ「Docker公式リポジトリ方式」が推奨されるのか

以下は、**学習用途であっても公式リポジトリ方式が有効である理由**である。

### 3.1 DockerをDockerとして学べる

- 公式ドキュメントと構成が一致する
- 他環境（クラウド、サーバ）へ知識を転用しやすい

### 3.2 ブラックボックスを避けられる

- GPG 鍵登録、リポジトリ追加を自分で確認できる
- 「何を信頼しているか」を把握できる

### 3.3 再現性・監査性が高い

- 手順書として残しやすい
- 将来の再構築・レビューが容易

---

## 4. 把握しておくべきリスク（特にスクリプト方式）

### 4.1 インストール時のリスク

- 外部コードを root 権限で即実行
- DNS / TLS / CDN への依存
- 実行時点で内容が変わる可能性

### 4.2 インストール後（運用時）のリスク

- どの設定が自動で入ったか分からない
- セキュリティ責任の所在が曖昧になりやすい
- トラブル時の切り分けが難しい

※ これらは **インストールが成功していても残るリスク**である。

---

## 5. インストール後に注意すべき代表的な設定項目

- Docker サービスの常駐起動の要否
- docker グループの扱い（root 相当権限）
- docker.sock の権限
- ネットワーク（iptables 等）への影響
- rootless Docker の検討

これらは **インストール方式に関係なく利用者が判断すべき事項**である。

---

## 6. Docker 導入結果の比較（公式スクリプト vs 公式リポジトリ）

以下は、Docker の **公式インストールスクリプト** と **Docker公式リポジトリ（手動設定）** による
インストール結果を、設定・動作・セキュリティ・運用観点から比較したものである。

> 評価基準
> - 差なし：結果・意味・責任範囲が実質同一
> - 差あり（軽）：結果は同じだが、可視性・制御性が異なる
> - 差あり（本質）：運用・セキュリティ・再現性に影響する

| 項目名 | インストールスクリプト | 公式リポジトリ | 差についての評価 |
|---|---|---|---|
| パッケージ提供元 | Docker公式 | Docker公式 | 差なし |
| 使用リポジトリ | 公式APT（自動追加） | 公式APT（手動追加） | 差なし |
| 取得されるバイナリ | 同一 | 同一 | 差なし |
| Docker Engine 初期動作 | デフォルト | デフォルト | 差なし |
| containerd / runc | 自動導入 | 明示的導入 | 差あり（軽） |
| systemd サービス登録 | 自動 | apt により自動 | 差なし |
| ★ サービス自動起動設定 | 有効 | 有効 | 差なし |
| ★ daemon.json の初期状態 | 未作成 | 未作成 | 差なし |
| ★ ネットワーク挙動（iptables 等） | Dockerデフォルト | Dockerデフォルト | 差なし |
| ★ docker グループ作成 | 自動 | 自動 | 差なし |
| ★ docker.sock 権限 | グループ書込可 | グループ書込可 | 差なし（重要） |
| ★ rootless Docker | 未設定 | 未設定 | 差なし |
| ★ GPG鍵の登録方法 | スクリプト内部処理 | 明示的に登録 | 差あり（本質） |
| ★ GPG鍵の保管場所 | スクリプト依存 | 利用者が把握 | 差あり（本質） |
| ★ リポジトリ定義ファイル | 自動生成 | 明示的に作成 | 差あり（本質） |
| OS判別ロジック | スクリプト内包 | 利用者判断 | 差あり（本質） |
| インストール時の確認可能性 | 低い | 高い | 差あり（本質） |
| 再現性（将来再構築） | 低い | 高い | 差あり（本質） |
| 監査・レビュー適性 | 低い | 高い | 差あり（本質） |
| トラブル時の切り分け | 困難 | 容易 | 差あり（本質） |
| ★ セキュリティ初期状態 | Dockerデフォルト | Dockerデフォルト | 差なし |
| ★ セキュリティ責任の自覚 | 生じにくい | 生じやすい | 差あり（本質・人的） |
| ★ 学習効果 | 低 | 高 | 差あり（本質・人的） |

### ★付き項目について

★ が付いている項目は、**インストール後に利用者が必ず確認・検討すべき設定項目**である。
これらはインストール方式によらず、Docker を安全かつ理解した上で運用するために重要となる。

---

## 7. 結論（設計方針として）

> Raspberry Pi である程度踏み込んだ構築を行う場合でも、
> 多くのパッケージ導入は原則として OS 標準リポジトリを使用する。
> ただし Docker については、Docker 公式リポジトリの利用が望ましい。

Docker のインストール方式の選択は、
**利便性ではなく「理解・制御・説明可能性」を基準に行うべきである。**

---

## 7. まとめ

- Docker には複数の正当なインストール方式が存在する
- 方式の違いは「結果」より「過程と責任」に現れる
- 学習用途であっても、理解を重視するなら公式リポジトリ方式が有効
